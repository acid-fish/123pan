## 1. 背景与需求

项目已具备单向文件夹同步（本地 → 云端，增量 + 指纹 + 定时 + 托盘后台）。本次需求在其基础上**新增双向同步**，且不得影响现有功能：

1. 侧边栏新增「双向同步」入口，位于「同步」与「回收站」之间，界面参考现有同步页；
2. 核心场景（A/B 双机）：
   - 白天在 A 电脑工作，下班关机前同步内容到云端；
   - 晚上在 B 电脑打开软件后，**静默**同步云端内容到本地（无弹窗、无需手动触发）；
3. 冲突处理默认采用「保留双方副本」；
4. 图标采用上下双向箭头，风格与现有 Fluent 图标一致。

## 2. 可行性分析结论

**可行**。现有代码已覆盖约 80% 能力，逐项核实如下：

| 双向同步所需能力 | 现状 | 证据 |
| --- | --- | --- |
| 本地→云端增量上传（指纹/覆盖/建目录） | ✅ | `service/sync_service.py:run_sync` |
| 云端目录递归索引（force_refresh） | ✅ | `SyncService.build_remote_index` |
| 云端→本地下载（多线程分片/断点续传/限速/429 退避） | ✅ | `DownloadService.download_file` + `api/download_engine.py` |
| 按文件获取下载链接 | ✅ | `DownloadService.link_by_fileDetail` |
| 远端文件时间戳字段 `UpdateAt` | ✅ | `api/model.py`（解析 `UpdateAt/updateAt`） |
| 后台调度 + 托盘 + 懒加载导航框架 | ✅ | `tasks/sync_manager.py`、`view/main_window.py` |
| SQLite 幂等建表（可追加新表） | ✅ | `common/database.py:_create_tables` |

缺口仅 5 项：pull 方向变更计算、双向状态表、冲突策略、启动静默同步触发、新页面与 i18n。

## 3. 总体设计决策

### 3.1 隔离式新增（核心原则）

**不修改** `SyncService` / `SyncManager` / `SyncStore` / `SyncInterface` 的任何现有逻辑。
双向同步使用独立模块、独立数据表、独立调度器，仅通过继承复用 `build_local_index` /
`build_remote_index` 两个纯函数方法。现有文件只有 `database.py` 与 `main_window.py`
做了**追加性**改动（不触碰原有代码行）。

### 3.2 状态模型（双端版本快照）

新增 `bi_sync_state` 表，按 `(job_id, rel_path)` 记录文件两端版本：

```
{local_size, local_mtime, remote_size, remote_updateat}
```

- 本地 `(size, mtime)` ≠ 快照 → 本地已改 → 上传；
- 云端 `(size, UpdateAt)` ≠ 快照 → 云端已改 → 下载；
- 两者同时变化 → 冲突，按策略处理；
- 上传成功并经云端列表验证后，直接写入验证返回的真实 `UpdateAt`（无需后续对齐）；
- `mtime` / `UpdateAt` 允许为 `NULL`（未知）：仅存在于历史/降级场景，
  保留“下次扫描按大小判断并补齐时间戳”的自愈逻辑向后兼容。

下载完成后用 `os.utime` 把本地 mtime 对齐云端 `UpdateAt`，保证 B 机拉取后的指纹与
A 机状态跨机可比，闭环成立：

```
A 改文件 → 上传 → 云端 UpdateAt 变化 → B 机同步发现 remote_updateat 不一致 → 自动拉取
```

### 3.3 变更计算矩阵

| 场景 | 处理 |
| --- | --- |
| 首次接触，两端大小一致 | 直接对齐快照，零传输 |
| 首次接触，两端大小不一致 | 视为冲突，按策略 |
| 仅本地变化 | 上传（统一 `dup_choice=2` 覆盖语义，同 MD5 由服务端复用避免 5060 竞态） |
| 仅云端变化 | 下载覆盖本地 |
| 双方同时变化 | 冲突：`keep_both`（默认）/ `local_wins` / `remote_wins` |
| 本地删除、云端未变 | `delete_remote` 开→删云端；关→保持不动 |
| 本地删除、云端已变 | 拉回本地（云端改动优先，不删云端） |
| 云端删除、本地未变 | `delete_local` 开且云端副本**此前被确认存在过** → 删本地；云端从未被确认 → 重新上传（绝不删本地）；`delete_local` 关 → 保持不动 |
| 云端删除、本地已变 | 重新上传（本地改动优先，不删本地） |
| 本地目录缺失于云端 | 云端建目录（顶层优先，按深度排序） |
| 云端目录缺失于本地 | 本地建目录；删除本地目录仅删空目录（自底向上） |
| 文件/目录同名冲突 | 跳过并计失败，不破坏任何一侧数据 |
| 两端都消失、仅剩快照 | 清理残留快照 |

### 3.4 冲突策略（默认「保留双方副本」）

本地与云端同时修改同一文件时：

1. 主路径保留本地版本，并将其上传覆盖云端（`dup_choice=2`）；
2. 云端版本下载另存为 `文件名（冲突副本 YYYYMMDD-HHMMSS）.ext`（重名自动加序号）；
3. 副本**不写快照**——作为全新本地文件，下次同步自动上传到云端。

结果：两侧最终都保有双方内容，不静默丢失任何一方的修改。另外可选
「以本地为准」（只上传）与「以云端为准」（只下载）。

### 3.5 启动静默同步（B 机场景）

`BiSyncManager.set_pan()`（登录成功时由 MainWindow 调用）中，
对全部 `sync_on_startup=1` 且启用的任务 `QTimer.singleShot(0)` 触发一次立即运行。
B 机开机自动登录后立刻在后台静默拉取云端变化：无对话框、无 InfoBar，
冲突按策略自动处理（默认保留双方副本），配合现有 `startMinimized`
设置可直接托盘后台运行。

## 4. 数据设计

`common/database.py::_create_tables` 追加三张表（`CREATE TABLE IF NOT EXISTS`，
老库启动时自动建表，零迁移风险）：

```sql
bi_sync_jobs (
  id, name, local_path, remote_dir_id, remote_dir_name,
  interval_seconds, enabled,
  delete_remote   INTEGER DEFAULT 0,   -- 本地删除→删云端
  delete_local    INTEGER DEFAULT 0,   -- 云端删除→删本地（默认关，更安全）
  conflict_policy TEXT DEFAULT 'keep_both',  -- keep_both | local_wins | remote_wins
  sync_on_startup INTEGER DEFAULT 1,   -- 登录后立即静默同步（默认开）
  last_run_at, created_at, updated_at
);

bi_sync_history (  -- 运行历史，在 sync_history 基础上增加 downloaded/conflicts 列
  id, job_id, job_name, started_at, finished_at,
  added, updated, downloaded, deleted, conflicts, failed, status, message
);

bi_sync_state (    -- 核心：每文件双端版本快照
  job_id, rel_path,
  local_size, local_mtime,        -- 本地版本（NULL=未知）
  remote_size, remote_updateat,   -- 云端版本（NULL=未知）
  PRIMARY KEY (job_id, rel_path)
);
```

## 5. 执行流程（一次 run）

```
安全闸：本地目录不存在 → 中止；build_remote_index 返回 None → 中止（防误删）
1. 扫描：build_local_index（符号链接防护）+ build_remote_index（force_refresh）
2. 变更计划：compute_bi_changes（含首次接触对齐、快照自愈、冲突路由）
3. 云端建目录（顶层优先）→ 4. 上传本地变化（up_load，统一覆盖语义 + token 过期自动重登；
   上传后回读云端目录**验证文件确实注册**，未确认→计失败且不写快照）
5. 本地建目录 → 6. 下载云端变化（link_by_fileDetail + download_file，
   cancel_event 适配器接入下载引擎；完成后 os.utime 对齐 UpdateAt）
7. 冲突副本下载（保留双方副本策略）
8. 删除云端多余条目（delete_remote，文件优先、目录自底向上，trash_file）
9. 删除本地多余条目（delete_local，文件 + 仅空目录）
10. 文件/目录同名冲突计失败 → 11. mark_all_dirs_dirty() 使文件页缓存失效
```

每个文件**成功后才写快照**（失败不写 → 下次自动重试）。阶段进度信号
（扫描本地/获取云端列表/上传/下载/删除）经 `_SyncJobSignals` 回主线程。

## 9. 设计要点与安全边界

- **与单向同步完全隔离**：独立表（bi_sync_*）、独立管理器、独立线程，
  同一账号可同时存在单向/双向任务，互不干扰；同一本地目录建议只建一种任务。
- **防误删三道闸**：远端索引失败即中止（`None` 语义保留）；本地目录缺失即中止；
  本地目录删除仅删空目录。
- **冲突零丢失**：默认保留双方副本，任何策略下都不静默覆盖两侧修改。
- **静默同步成本**：下载走既有 429/5xx 退避与限速设置；流量不弹窗、仅日志记录。
- **跨机一致性**：本地 mtime 对齐云端 `UpdateAt`，上传后时间戳自愈机制保证
  不会因服务端时间戳未知而产生冗余下载或漏同步。

# 12. 附录二：上传协议修复记录（2026-09-23 实测）

## 12.1 问题现象

真实环境测试发现：小文件（走秒传复用）可上传，但**新内容文件**（含大文件）
点击同步后显示“成功”，云端目录实际查不到该文件；再次同步时（勾选“云端删除时
同步删除本地文件”）会**直接删除本地文件**。

## 12.2 根因分析

证据链（真实账号逐步接口拦截 + 日志分析）：

1. 逐接口拦截发现旧上传协议各步骤全部返回 code=0（`upload_request` →
   `s3_list_upload_parts` → 分片 PUT → `s3_complete_multipart_upload`
   （响应 `Location` 为空）→ `upload_complete`（响应 data 为空）），
   但文件始终不出现在目录列表（含 `OnlyLookAbnormalFile=1` 异常文件视角），
   多次验证后确认：**服务端已废弃旧协议的合并/完成链路，接口返回成功但
   静默丢弃文件**。
2. 对照当前维护中的 alist 123 驱动（AlistGo/alist `drivers/123/upload.go`），
   新协议为：
   - 分片大小取 `upload_request` 返回的 `SliceSize`（现为 16MB）；
   - 单块文件走 `POST /b/api/file/s3_upload_object/auth` 取预签名 URL，
     多块走 `POST /b/api/file/s3_repare_upload_parts_batch`；
   - 完成时调用 **`POST /b/api/file/upload_complete/v2`**，载荷
     `{StorageNode, bucket, fileId, fileSize, isMultipart, key, uploadId}`，
     **不再调用** `s3_complete_multipart_upload` 与旧 `upload_complete`；
   - 成功响应携带完整 `file_info`（FileId/Size/Etag/UpdateAt 等）。
3. 本实现此前还有两个防护缺口：
   - 上传后直接写快照（云端时间戳记 NULL），服务端静默丢弃时快照照写；
   - `delete_local` 分支未区分“云端副本从未被确认”，导致二次同步把
     本地文件当作“云端已删除”而删除（数据丢失）。

## 12.3 修复内容

| 文件 | 修复 |
| --- | --- |
| `src/app/service/upload_service.py` | ① 分片大小改为服务端 `SliceSize`（缺省 16MB）；② 单块文件改用 `s3_upload_object/auth` 端点；③ 完成确认改用 `upload_complete/v2`（富载荷，移除旧的合并/确认调用与 >64MB sleep）；④ 完成响应缺 `file_info` 时延迟重试 3 次（抵御服务端偶发未注册）；⑤ 旧续传会话分片大小不匹配时作废重传（避免分片边界错位） |
| `src/app/service/bi_sync_service.py` | ① 上传统一 `dup_choice=2`（同 MD5 触发服务端复用，避免 5060 竞态）；② **上传后回读父目录列表验证文件确实注册**（3 秒后复查一次），未确认→计失败且不写快照，下次同步自动重传；③ 快照直接写入云端列表返回的真实 `UpdateAt`（无需后续自愈）；④ `delete_local` 增加护栏：**云端副本从未被确认存在（remote_updateat=NULL）时绝不删除本地文件**，改为重新上传；⑤ `run_bi_sync` 新增 `refresh_session` 参数并透传 `up_load`/上传验证，**token 过期时自动重登重试** |
| `src/app/tasks/bi_sync_tasks.py` | 同步线程传入 `refresh_session=self._pan.login`（与 UI 上传路径一致的自动重登） |
